# Архитектура проекта

Система построена по трёхзвенной схеме: браузер с React-приложением обменивается данными с API на Node.js, сервер хранит данные в PostgreSQL. Репозиторий — монорепозиторий npm workspaces с каталогами `client` и `server`. Компонентная диаграмма сервера: `docs/Диаграммы PlantUML/component.puml`.

## Клиент

Клиент — одностраничное приложение на React 19 и Vite. Маршруты закодированы в хэше адреса (HashRouter): GitHub Pages отдаёт один `index.html`, серверные маршруты ему недоступны. Страницы собраны в `client/src/pages`: вход, регистрация, чат, каталог каналов, администрирование. Общие элементы — шапка, панель каналов, окно чата, панель участников — лежат в `client/src/components`.

Клиент хранит пару токенов в `localStorage`. Axios-клиент (`client/src/api/client.ts`) подставляет заголовок `Authorization` в каждый запрос; при ответе 401 один раз обновляет пару и повторяет запрос, при неудаче завершает сессию. Адрес API задаётся при сборке переменной `VITE_API_URL` (`client/.env.production`), адрес WebSocket клиент выводит из неё же. WebSocket-подключение к активному каналу ведёт хук `useChannelSocket`; ширина боковых панелей меняется мышью за счёт хука `usePanelResize`.

## Сервер

Сервер разделён на слои с односторонними зависимостями:

| Слой          | Модули                                | Ответственность                  |
| ------------- | ------------------------------------- | -------------------------------- |
| `controllers` | `auth`, `channel`, `message`, `admin` | HTTP-маршруты и разбор запросов  |
| `services`    | `auth`, `channel`, `message`, `admin` | бизнес-логика и обращения к базе |
| `data-access` | `prisma`                              | клиент Prisma                    |
| `gateway`     | `ws`                                  | WebSocket-транспорт              |
| `middleware`  | `auth`                                | проверка токена и ролей          |

Функция `createHttpServer()` (`server/src/app.ts`) поднимает REST API и WebSocket-шлюз на одном HTTP-сервере — так сценарные тесты обращаются к API и к `/ws` через один адрес. Точка входа `index.ts` запускает сервер в рабочем режиме. Контроллеры не содержат бизнес-логики, сервисы не содержат транспорт — это соответствует компонентной диаграмме.

### REST API

| Маршрут                                  | Метод     | Назначение                          |
| ---------------------------------------- | --------- | ----------------------------------- |
| `/api/auth/register`                     | POST      | регистрация сотрудника              |
| `/api/auth/login`                        | POST      | вход, выдача пары токенов           |
| `/api/auth/refresh`                      | POST      | обновление пары токенов             |
| `/api/auth/logout`                       | POST      | отзыв токена обновления             |
| `/api/auth/me`                           | GET       | данные текущего сотрудника          |
| `/api/channels`                          | GET, POST | каналы сотрудника, создание канала  |
| `/api/channels/catalog`                  | GET       | каталог публичных каналов           |
| `/api/channels/:id/join`                 | POST      | вступление в публичный канал        |
| `/api/channels/:id/members`              | GET, POST | состав канала, добавление участника |
| `/api/channels/:id/members/:userId`      | DELETE    | исключение участника                |
| `/api/channels/:id/members/:userId/role` | PATCH     | смена локальной роли                |
| `/api/channels/:id/messages`             | GET       | лента сообщений канала              |
| `/api/admin/users`                       | GET       | реестр сотрудников                  |
| `/api/admin/users/:id/status`            | PATCH     | блокировка и разблокировка аккаунта |
| `/api/admin/users/:id/role`              | PATCH     | назначение и снятие роли `ADMIN`    |

### Протокол WebSocket

Клиент подключается к `/ws?token=<accessToken>`; сервер проверяет токен при рукопожатии. Данные передаются фреймами в формате JSON.

| Направление     | Тип фрейма        | Содержимое                         |
| --------------- | ----------------- | ---------------------------------- |
| клиент → сервер | `subscribe`       | `channelId`                        |
| клиент → сервер | `send`            | `channelId`, `content`             |
| клиент → сервер | `delete`          | `messageId`                        |
| сервер → клиент | `subscribed`      | подтверждение подписки на канал    |
| сервер → клиент | `message`         | сообщение: автор, дата, текст      |
| сервер → клиент | `message.deleted` | идентификатор удалённого сообщения |
| сервер → клиент | `error`           | описание отказа                    |

Сервер рассылает сообщение только подписчикам канала. Удаление сообщения проходит проверку прав в сервисе сообщений: удалять чужое сообщение могут модератор и владелец канала.

## База данных

СУБД — PostgreSQL 17, доступ к ней — через Prisma 7 и драйвер `@prisma/adapter-pg`. Схема (`server/prisma/schema.prisma`) описывает пять таблиц.

| Таблица           | Содержимое                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| `users`           | сотрудники: имя, email, хэш пароля, глобальная роль (`USER`, `ADMIN`), статус (`ACTIVE`, `BLOCKED`) |
| `refresh_tokens`  | хэши токенов обновления (SHA-256), срок действия, отметка отзыва                                    |
| `channels`        | каналы: название, тип (`PUBLIC`, `PRIVATE`)                                                         |
| `channel_members` | членство в канале: локальная роль (`OWNER`, `MODERATOR`, `MEMBER`)                                  |
| `messages`        | сообщения: автор, канал, текст, дата                                                                |

Связи между таблицами настроены с каскадным удалением: удаление сотрудника или канала убирает его токены, членства и сообщения.

## Аутентификация и сессии

Сессия опирается на пару токенов JWT (HS256). Токен доступа действует 15 минут и подтверждает каждый запрос. Токен обновления действует 7 дней: сервер хранит его в виде хэша SHA-256, а обновление сессии отзывает старый токен и выдаёт новую пару. Выход из системы отзывает токен обновления. Пароли хэширует bcrypt с 10 раундами соли; открытый пароль сервер не сохраняет.

## Ролевая модель

Система использует две независимые иерархии ролей. Глобальная роль (`USER`, `ADMIN`) определяет доступ к панели администратора; проверка читает роль из базы при каждом запросе, поэтому смена роли действует немедленно. Локальная роль в канале определяет права на управление составом и сообщениями.

| Действие                  | `OWNER` | `MODERATOR` | `MEMBER` |
| ------------------------- | ------- | ----------- | -------- |
| Добавление участников     | да      | да          | нет      |
| Исключение участников     | да      | нет         | нет      |
| Смена локальных ролей     | да      | нет         | нет      |
| Удаление чужого сообщения | да      | да          | нет      |

Чужие приватные каналы скрыты из каталога: их существование для посторонних незаметно. Состав канала и лента сообщений доступны только участникам.

## Инфраструктура

Тесты написаны на Vitest, Supertest и `ws` и выполняются в отдельной базе `corp_messenger_test`; все таблицы обнуляются перед прогоном и после него. Набор покрывает весь код на 100 % и включает модульные, интеграционные, сценарные, нагрузочные тесты и матрицу ролевых ограничений. Конвейер GitHub Actions проверяет форматирование и линтеры, запускает тесты с контейнером PostgreSQL 17, собирает клиент и сервер, публикует метрики качества, а после слияния в `main` разворачивает клиент на GitHub Pages.
